## 詳細

### Q-01 計算単位（月次 / 年次）
- **選択肢**: A) 月次計算・年次集計　B) 年次計算のみ　C) 年次計算＋ローンのみ月次
- **推奨**: A
- **理由**: ローン返済・賞与月・学齢（4月）・誕生月による年齢到達・年途中の転職など月単位の事象が多い。年次のみだと「年途中のイベントは年初/年末どちらで計上するか」という近似が多数生じる。計算量（最大 1,320 か月）は問題にならない。
- **影響**: エンジン全体の構造。後から変更困難。

### Q-02 年次集計の区切り
- **選択肢**: A) 暦年（1〜12 月）　B) 年度（4〜3 月）　C) 本人の年齢年（誕生月〜）
- **推奨**: A（表示切替として B・C を P2 で追加可能。月次データを持つため集計方法だけの変更で済む）
- **理由**: 税・年金制度は暦年が多く、直感的にわかりやすい。教育費は年度単位だが月次で計上するので集計区切りとは独立。

### Q-03 生年月日の精度
- **選択肢**: A) 年月のみ　B) 年月日
- **推奨**: A
- **理由**: 月次計算には日は不要。学齢判定で4月1日生まれのみ影響するが、例外的なので「4月生まれは4/2以降扱い」と仕様化する。個人情報の保持も最小化できる。
- **懸念**: 4月1日生まれの子がいる場合1学年ずれる → B にするか、子のみ「早生まれ扱い」チェックを持たせる案もある。

### Q-04 「X 歳まで」の解釈
- **選択肢**: A) X 歳になる前月まで（X 歳未満）　B) X 歳の最終月まで（X+1 歳の前月）　C) 選択式
- **推奨**: C（既定 A）
- **理由**: 「60 歳まで働く」は「60 歳の誕生月まで/60 歳の年度末まで」など人により意味が異なり、1 年ずれると結果に大きく影響する。UI で明示的に選ばせる方が誤解がない。定年は「X 歳到達の年度末（3月）」指定も可能にする（Trigger の `month` 指定）。

### Q-05 丸め方法
- **選択肢**: A) 仕訳時に四捨五入・ローンは切り捨て　B) すべて切り捨て　C) 丸めずに浮動小数で保持し表示時のみ丸め
- **推奨**: A
- **理由**: C は残高恒等式を厳密に検証できず、長期で誤差が累積する。ローンは実務（多くの金融機関）の切り捨てに合わせる。ただし金融機関により異なるため、将来的にローンごとの設定を検討。

### Q-06 税・社会保険の扱い（初期版）
- **選択肢**: A) 手取り入力のみ　B) 額面入力＋実効税率（利用者入力）で簡易推計　C) 制度に基づく計算
- **推奨**: A（v1.0）。B を v1.x の最初の拡張、C は将来
- **理由**: C は扶養・配偶者控除・社保の等級・住民税の翌年課税・制度改正対応など仕様が膨大で、誤った制度計算はむしろ判断を誤らせる。手取りは給与明細・源泉徴収票から利用者が把握できる。
- **懸念**: 昇給による税率上昇（累進）が反映されず、高収入時の手取りを過大評価しうる → 画面に注記。

### Q-07 運用利回り
- **選択肢（換算）**: A) 幾何換算 `(1+r)^(1/12)−1`　B) 単純 `r/12`
- **選択肢（課税）**: A) 税引後利回りを入力　B) 税前利回り＋課税計算
- **推奨**: 換算 A・課税 A
- **理由**: 幾何換算は「年 r% で 1 年運用すると r% 増」が入出金なしで成立し、利用者の直感と一致する。課税計算は取得価額管理が必要で P2 とする。

### Q-08 支出合計の定義
- **選択肢**: A) 損益ベース（頭金・元本返済・積立は支出に含めない）＋現金増減を別表示　B) 現金ベース（出ていくお金はすべて支出）
- **推奨**: A
- **理由**: 二重計上（資産が増えたのに支出でも減る）を防ぎ、純資産の説明と整合する。ただし家計感覚では「ローン返済額＝支出」なので、年次表に「現金の増減」列と「ローン返済額（元本+利息）」列を併記して両方わかるようにする。

### Q-09 シナリオの持ち方
- **選択肢**: A) 完全コピー（各シナリオが独立した全データ）　B) 基準シナリオ＋差分（オーバーライド）
- **推奨**: A（v1）
- **理由**: B は「基準を変えると派生がすべて変わる」利点があるが、差分の表現・競合・削除済み項目の扱いが複雑。v1 は A で実装し、データモデルは B に移行可能な形（ID 安定・`copiedFrom` 保持）にしておく。
- **影響**: 「基準データを直したのに他シナリオに反映されない」不便がある → 複数シナリオへの一括反映は P2 で検討。

### Q-10 上昇率の適用月
- **推奨**: 給与系は 4 月、その他は 1 月。項目ごとに変更可能。
- **理由**: 日本の一般的な昇給時期。物価は暦年。

### Q-11 年金の伸び
- **推奨**: 既定は名目一定（保守的）、任意で年率スライドを入力。
- **理由**: マクロ経済スライドにより物価ほど増えない可能性が高く、物価連動を既定にすると過大評価のおそれ。

### Q-12 不動産評価
- **推奨**: P1 は年率変動（既定 −1.5%/年 等、利用者入力）のみ。
- **理由**: 不動産は売却しない限り資金計画に直接影響しないため、単純なモデルで十分。純資産グラフには影響するので「金融資産」表示も用意する。

### Q-13 資金不足の扱い
- **選択肢**: A) マイナス許容＋警告　B) 自動取り崩し（順序指定）　C) 計算停止
- **推奨**: A を既定、B をオプション
- **理由**: どこでいくら不足するかを可視化することが目的。自動取り崩しは現実的だが、投資の取り崩しが隠れて「不足していない」ように見えるため既定 OFF。ON の場合は取り崩し額を明示表示。

### Q-14 UI フレームワーク
- **選択肢**: React / Vue / Svelte
- **推奨**: React + Vite + TypeScript
- **理由**: グラフ・フォーム・テストのライブラリが最も充実し、将来の機能追加で困りにくい。利用者側に特定の好み・既存資産があれば合わせる。

### Q-15 保存方式
- **選択肢**: localStorage / IndexedDB (idb-keyval) / IndexedDB (Dexie) / OPFS
- **推奨**: IndexedDB + idb-keyval
- **理由**: データは 1 ドキュメント（数百 KB 未満）で足りるため単純な KV で十分。localStorage は同期 API・容量制限（約 5MB）・退避世代を持つと逼迫するおそれ。

### Q-16 自動退避の世代数
- **推奨**: 5 世代（インポート前・全削除前・1 日 1 回の自動退避）

### Q-17 配布・利用方法
- **選択肢**: A) ローカルで `npm run preview`　B) GitHub Pages 等の静的ホスティング（データはブラウザ内のまま）　C) ビルド済み HTML をファイルで開く
- **推奨**: 開発中は A、v1.0 で B を検討
- **理由**: B でもデータは端末内に留まるが、配布 URL のオリジンに IndexedDB が紐づくため、URL 変更でデータが見えなくなる点に注意（エクスポートで移行）。リポジトリが公開/非公開かも確認が必要。

### Q-18 既定値
- **推奨**: 物価上昇率 1.5%、運用利回り（税引後）3.0%、車両減価 −15%/年、不動産 −1.5%/年
- **理由**: いずれも「あくまで初期値」であり、画面で利用者に確認を促す。根拠（日銀の物価目標 2% より保守的、等）は前提画面に記載。

### Q-19 教育費等テンプレート
- **推奨**: 公的統計（文部科学省「子供の学習費調査」、日本政策金融公庫「教育費負担の実態調査」等）を、調査年を明記して既定値に採用。値は Phase 2 で調査・記載し承認を得る。
- **理由**: 既定値の根拠を示せないと結果の信頼性を判断できない。

### Q-20 エクスポートの暗号化
- **推奨**: v1 は非暗号化。ファイルの取り扱い注意を画面に表示。
- **理由**: パスワード忘れによるデータ喪失リスクと実装コスト。必要性が高ければ Web Crypto (AES-GCM + PBKDF2) で P2 に前倒し可能。

### Q-21 生活口座の数
- **推奨**: v1 は世帯で 1 つ。
- **理由**: 夫婦別財布や口座間の資金移動を正確に表現するには、どの収入・支出がどの口座かを全項目で指定する必要があり入力負担が大きい。データモデルは口座 ID を持たせておき、P2 で拡張可能にする。

### Q-22 スマートフォン対応
- **推奨**: v1 は PC 最適化。スマホでは表示崩れなく閲覧・簡易編集できる水準。
