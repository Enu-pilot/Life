# LifePlan テスト戦略

- 文書状態: 承認済み（2026-10-26）。実装に合わせて随時更新
- 最終更新: 2026-10-26

---

## 1. 原則

1. **期待値は実装と独立に求める**。手計算、または `tools/verify/` の独立実装（Python。エンジンのコードを参照・移植しない）で算出し、算出方法をテストケースに記録する。
2. **テストを通すために期待値や仕様を変更しない**。不一致が出たら「実装の誤り」「期待値算出の誤り」「仕様の曖昧さ」のどれかを特定し、仕様の曖昧さなら open-questions.md に起票して判断を仰ぐ。
3. 計算エンジンは UI なしで（Node 上の Vitest で）すべてテストできる。
4. 金額の比較は**完全一致（1円の誤差も許容しない）**。整数円仕訳設計（calculation-spec §3）により可能。浮動小数を経由する率計算の中間値は比較しない。
5. 各 Phase 終了時に全テスト（回帰テスト）を実行し、結果を報告する。実行していないテストを成功と報告しない。

## 2. テストレベルと担当範囲

| レベル | ツール | 対象 | 実行タイミング |
|---|---|---|---|
| 単体 | Vitest | engine の各モジュール（time / triggers / loan / ledger / events / aggregate / validate）、storage のマイグレーション・検証 | 常時（`npm test`） |
| ゴールデン | Vitest + JSON fixture | 代表シナリオの年次結果を独立実装の出力と完全一致比較 | 常時 |
| プロパティ | Vitest + fast-check | 不変条件をランダム生成シナリオで検証 | 常時（回数を CI/ローカルで調整） |
| コンポーネント | Vitest + Testing Library (jsdom) | フォームのバリデーション表示、空状態表示 | 常時 |
| E2E | Playwright（Chromium） | ui-design.md §6 の主要操作フロー、IndexedDB 永続化、エクスポート/インポート | Phase 3 以降、各 Phase 終了時 |

カバレッジ目標: `src/engine` 行 90% 以上・分岐 85% 以上、`src/storage` 行 90% 以上。UI は数値目標を置かず主要フローを E2E で担保する。

## 3. 計算エンジンの単体テスト（主要ケース）

### 3.1 時間・年齢

| ケース | 期待値（手計算） |
|---|---|
| 生年月 1990-05、2026-04 の年齢 | 35 |
| 同、2026-05（誕生月） | 36 |
| 子 2020-03 生まれの小学校入学 | 2026-04（早生まれ: 生年+6） |
| 子 2020-04 生まれの小学校入学 | 2027-04（生年+7、4月生まれは4/2以降扱い） |
| 子 2019-12 生まれの大学入学 | 2038-04 |
| `monthIndex` ⇔ `YYYY-MM` の相互変換 | 1900-01, 1999-12, 2000-01, 2100-12 で往復一致 |

### 3.2 ローン（元利均等）

独立計算（Python `decimal`、50 桁精度）による期待値:

| 条件 | 期待値 |
|---|---|
| 借入 30,000,000 円、年 1.2%、420 回、元利均等、返済額・利息とも円未満切り捨て | 毎月返済額 87,510 円 / 初回利息 30,000 円・初回元本 57,510 円 / 最終回返済額 87,611 円 / 総利息 6,754,301 円 / 完済後残高 0 円 |

その他のケース: 金利 0%（返済額 = 借入額 / 回数、端数は最終回）、1 回払い、元金均等、変動金利の途中変更、期間の途中から開始。

### 3.3 運用

| 条件 | 期待値 |
|---|---|
| 1,000,000 円、年 3%（幾何月次換算）、入出金なし、12 か月、月次損益を四捨五入 | 12 か月後 1,030,000 円（Phase 1 で独立スクリプトにより再確認） |
| 利回り 0% | 残高不変 |
| 利回り負（−10%） | 残高減少、マイナスにならない |
| 当月入金分に当月の運用益が付かない | 月初 0 円・月中 100,000 円入金 → 当月損益 0 円 |

### 3.4 収支項目

- 期間の両端を含む（開始月・終了月に計上、前後の月に計上なし）
- 頻度: 毎月 / 毎年◯月 / 賞与 [6,12] の発生回数が期間内で正しい（例: 2027-01〜2029-12 の賞与は 6 回）
- 上昇率: 月額 300,000 円、年 2%、4 月適用 → 開始 2027-01 のとき 2027-03 は 300,000、2027-04 は 306,000、2028-04 は 312,120
- 物価連動: シナリオの物価上昇率変更が反映される
- 年齢指定の終了: 「X 歳になる前月まで」と「X 歳の間も含む」の差が 12 か月

## 4. 境界値・異常値テスト

| 区分 | ケース | 期待 |
|---|---|---|
| 期間 | 開始月 = 終了月（1 か月のみ） | 正常計算 |
| 期間 | 終了年齢 110、開始時点 0 歳（約 1,320 か月） | 正常計算、性能 50ms 以内 |
| 期間 | 生年月が開始年月より後 | 検証エラー |
| 金額 | 0 円の項目 | 仕訳を作らない（0 円仕訳なし） |
| 金額 | 上限 1,000 億円 | 正常（安全整数内） |
| 金額 | 負数・小数・NaN・文字列 | 検証エラー |
| 率 | −50%、+50% / 範囲外 | 正常 / エラー |
| 参照 | 存在しない口座・メンバー・項目 ID を参照 | 検証エラー（計算しない） |
| イベント | 発生月が期間外 | 警告、計算は継続 |
| イベント | 同一 ID のイベント 2 件 | 検証エラー |
| ローン | 借入額 > 物件価格 | 検証エラー |
| 資金不足 | 現金がマイナス | 継続計算、指標に初回月・最大額 |
| 資金不足 | 自動取り崩し ON、投資残高不足 | 取崩は残高上限、残りはマイナス |

## 5. 人生イベントの反映テスト

イベント種別ごとに次を確認する。

1. **生成物**: 期待される派生収支・口座・一時仕訳がすべて生成される（計上漏れ防止）。
2. **一意性**: 同じ展開を 2 回実行しても仕訳は 1 回分（エンジンの一意キー検査が機能する）。
3. **終了指定**: `endsItemIds` に指定した項目が発生月の前月で止まり、発生月以降に仕訳がない。
4. **無効化**: `enabled: false` のイベントは結果に一切影響しない（無効化した結果 = イベントを削除した結果、を完全一致で確認）。
5. **会計的整合**: 住宅購入月の純資産変化 = −諸費用のみ（頭金・借入は資産と負債の振替であり純資産を変えない）。
6. 住宅購入例（手計算可能な小さい数値で作る）: 物件 1,000 万円、頭金 200 万円、諸費用 50 万円、借入 800 万円・0%・80 回 → 購入月に cash −250 万円、property +1,000 万円、loan +800 万円、翌月から毎月 cash −10 万円・loan −10 万円、80 回で loan 0。
7. 出産 → 教育費: 子の生年月から学齢が正しく決まり、各段階の費用が正しい年度（4月〜翌3月）に計上される。

## 6. シナリオ比較テスト

- 複製直後のシナリオは元と完全に同一の結果（ID 以外）。
- 複製後に片方を変更しても他方は不変（深いコピー、ID 振り直しと参照の変換が正しい）。
- 比較指標（指定年齢時点の純資産、最低現金残高、資金不足初回年齢）が各シナリオ単独の結果と一致。
- 前提（開始年月・物価上昇率等）が異なるシナリオを比較すると警告が出る。

## 7. データ保存・復元テスト

| ケース | 期待 |
|---|---|
| エクスポート → インポートの往復 | データが深い等価、計算結果が完全一致 |
| 旧スキーマ（fixture）→ マイグレーション | 現行スキーマに適合、意味的に等価（スキーマ版ごとに fixture を保管し、削除しない） |
| 新しすぎるスキーマ版 | 読込拒否、既存データ不変 |
| 壊れた JSON / 別アプリの JSON / 必須欠落 / 型違い | 失敗、エラー箇所表示、既存データ不変 |
| integrity 不一致 | 警告表示 |
| 未知フィールド | 除去される |
| インポート確定時 | 置換前データが退避世代に存在する |
| IndexedDB 書込失敗（モック） | 保存エラー状態になり、メモリ上のデータは保持 |

## 8. UI の主要操作テスト（E2E）

ui-design.md §6 のフロー 1〜5 を Playwright で自動化。加えて:

- ページ再読み込み後に入力が保持される（IndexedDB）

## 9. 長期間シミュレーションの整合性検証

全ゴールデン・プロパティテストで次の不変条件を**全月**について検証する（calculation-spec §5.2）。

1. 口座残高恒等式（期首 + 流入 − 流出 = 期末）が誤差 0 円で成立
2. 純資産の増減 = 収入 − 支出 + 運用損益 + 評価損益（誤差 0 円）
3. 年次集計 = 月次の合計（フロー）、年末月の残高（ストック）
4. 一意キー重複なし、0 円仕訳なし、全仕訳金額が正の整数
5. ローン残高は単調非増加（繰上・借増しなし時）で、最終回後 0
6. 投資・実物資産残高は非負

**プロパティテスト**: fast-check で、メンバー・収支項目・口座・イベントをランダムに組み合わせたシナリオ（最大 110 年）を生成し、上記不変条件を検証する。失敗時は最小反例を fixture として保存し回帰テスト化する。

**独立実装との突き合わせ（ゴールデン）**: 以下の代表シナリオについて、`tools/verify/` の Python 独立実装で年次結果を算出して JSON に保存し、エンジン結果と完全一致比較する。

| ID | シナリオ |
|---|---|
| G-01 | 単身・給与と生活費のみ・運用なし（手計算可能） |
| G-02 | 単身・積立投資あり・定年・年金 |
| G-03 | 夫婦・子 2 人・教育費・賃貸のみ |
| G-04 | 夫婦・子 1 人・住宅購入（元利均等 35 年）・車買い替え 3 回 |
| G-05 | 資金不足が発生するシナリオ（自動取り崩し ON/OFF） |

独立実装と仕様の解釈が食い違った場合は、どちらかに合わせて変更する前に仕様書の記述を確認し、曖昧なら起票する。

## 10. テストデータ管理

- `tests/fixtures/`: サンプルシナリオ、各スキーマ版の保存データ（マイグレーション用）。
- `tests/golden/`: ゴールデンケースの入力と期待値。期待値ファイルには算出方法（手計算 / 独立実装のバージョン）を記載。
- 期待値ファイルの更新は、仕様変更の承認とセットでのみ行う。更新時はコミットメッセージに理由と承認の参照を記載する。
